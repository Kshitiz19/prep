# Purpose of gemm application is to master high-performance gemm on cuda

The SOL anchor for GEMM: in theory it's compute-bound (arithmetic intensity ≈ N/6 FLOP/byte, which is huge), so the target is the FMA peak. But a naive kernel re-reads A and B so many times that it's wildly memory-bound in practice. Every rung increases data reuse, which raises your effective arithmetic intensity and walks you up the roofline toward compute peak. (Percentages below are from the canonical fp32 A6000 walkthrough — Simon Boehm's — and are illustrative, not portable, but the shape of the climb is universal.)

Naive — one thread per output element, reads straight from global. (~1% of cuBLAS.) SOL section shows both throughputs low → latency-bound. Tell: dominant warp stall is Stall Long Scoreboard (waiting on global memory), and Memory Workload Analysis shows high sectors-per-request (uncoalesced) with low achieved DRAM bandwidth. You're not even using the bandwidth you have.
Global memory coalescing — re-index so consecutive threads in a warp touch consecutive addresses. (~8%.) Sectors-per-request collapses to the minimum, achieved DRAM throughput jumps toward HBM peak. Now you flip to memory-bound: Memory % high, Compute % low. New wall: you're saturating HBM because there's zero reuse.
Shared-memory tiling — stage a BM×BK tile of A and BK×BN of B in SMEM, compute on it. (~13%.) Cuts global traffic by roughly a factor of the tile dimension, so DRAM throughput drops (good — that's reuse). The wall moves into shared memory: watch Stall Short Scoreboard / Stall MIO Throttle (waiting on SMEM) and the shared-memory bank-conflict counter. Compute SOL is still low because each thread does too little arithmetic per SMEM load.
Register blocking (1D then 2D blocktiling) — each thread computes a TM×TN tile of outputs accumulated in registers, via outer products. (1D ~36%, 2D ~68% — the single biggest jump.) Reuse moves from SMEM into registers, so SMEM loads per FLOP plummet and arithmetic intensity per thread soars. This is the rung that finally drives FMA pipe utilization (Compute SOL) up hard while SMEM stalls fall. The tension to watch: register blocking raises registers-per-thread, which can crater achieved occupancy or cause local-memory spills (Long Scoreboard reappears). The sweet spot is often lower occupancy with enough ILP to hide latency anyway — confirm via the SASS that there's no local-memory traffic.
Vectorized loads (LDG.128 / LDS.128 / float4) + bank-conflict-free SMEM. (~74%.) Wider loads mean fewer issued instructions and better memory-level parallelism; check the SASS for LDG.E.128/LDS.128 and watch issued-instruction count and MIO Throttle drop. Transpose the A tile in SMEM so its column reads vectorize. Then kill bank conflicts (padding or a swizzled layout) — the bank-conflict counter should hit ~0 and the shared-memory stalls with it.
Warptiling — insert a warp-level tile between the block tile and the thread tile. (~93%+.) Organizes the register tile so a warp reuses operands cleanly, lowering register pressure for a given output footprint and improving ILP. FMA pipe utilization approaches peak with balanced stalls — at this point most remaining stall is Stall Not Selected, which is the good one (plenty of eligible warps, the scheduler just can't issue them all — you're issue-bound at near-peak).
Double-buffering / cp.async multi-stage pipelining — prefetch the next tile's global→shared load while computing the current one. Hides the last of the global latency. The tell: residual Stall Long Scoreboard drops further and Compute SOL nudges to the CUDA-core ceiling. This is exactly the async-pipeline machinery from before, now earning its keep.

At this point you're near the CUDA-core FMA peak — and here's the punchline that motivates everything in the last message: that peak is roughly an order of magnitude below the tensor-core peak (on A100, ~19.5 fp32 TFLOPs vs ~312 fp16 tensor-core TFLOPs). So a "great" 93%-of-cuBLAS SGEMM is still leaving a 10× factor on the floor for fp16/bf16. The transition:
Tensor-core GEMM. Replace the inner register-tile FMA accumulation with wmma → then mma.sync (→ wgmma on Hopper) operating on fragments. The SOL gauge changes: you now read Tensor (Core) Pipe Utilization / Tensor Active % in Compute Workload Analysis instead of FMA pipe %. And the wall immediately flips back to memory — tensor cores consume operands so fast that they starve instantly. So if Tensor Active % is low while you're "using tensor cores," you are feeding them too slowly: add pipeline stages, switch to TMA bulk async copies, swizzle SMEM so the fragment loads don't bank-conflict, and on Hopper adopt the producer/consumer warp-specialized structure. You're done when Tensor Active % sits near peak and your dominant stall is again the benign Not-Selected. This is also the exact moment CUTLASS stops being a black box — you've now hand-built a slower version of precisely what it assembles for you.
